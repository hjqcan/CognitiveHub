# 接入已有宿主，而不是再造一个控制中心

## 机器人管理平台

建议先接入现有流程的“需要情境判断”节点。RMS/RBS 继续拥有正式任务、派发、状态、资源与执行生命周期；能力插件只通过这些既有接口请求操作。

```text
RMS 任务受阻节点
    → Hub.propose(intent)
    → 查看受约束的候选提案
    → 宿主批准，Hub.execute(..., { live: true })
    → 能力插件调用 RMS/RBS 既有服务
    → 回执/事件到达，Hub.reconcile(recordId)
```

不要同时让 Hub 与原平台争夺同一任务状态机。空间规划仍处理几何与可行性；资源调度仍由平台处理；安全 PLC/控制器仍独立运行。

平台层暴露“请求恢复”“请求重规划”等能力。机器人层可以暴露更细的技能，但不能绕过平台抢占别人的资源。每个宿主选择合适的粒度。

`examples/robot-platform.mjs` 演示的是假的内存任务网关，不是固尔琦生产接口的实现。正式网关至少需要：

1. 接收稳定幂等键和预期状态版本，原子检查当前授权和所有权。
2. 返回受理句柄，能按句柄或幂等键查询未知结果。
3. 提供可以核验实际效果的数据，不仅是“请求已收到”。

## 人形机器人

同一内核，替换 StateProvider 和能力插件。感知、定位、导航、操作规划与安全由机器人原有系统完成。

Hub 不直接从摄像头图像产生关节动作。Jev 当前适配器输入是文本/JSON，状态适配器应明确区分真实观测、他人报告和未知信息。

已有技能可包装成“观察区域”“请求规划”“执行已验证计划”。计划 ID、目标对象、坐标系版本等由宿主绑定；模型选择候选，不创造任意控制指令。

## C# / .NET

核心当前是 TypeScript，不提供已经编译验证过的 .NET SDK。不要在 .NET 项目里假装 `AddCognitiveHub()` 已存在。

近期有两种合理路径：

- 在一个内部 TypeScript 服务里嵌入 Hub，能力插件调用既有 ASP.NET Core/RBS 服务。
- 后续按本仓库 JSON 契约实现 .NET 接入端，复用宿主任务与权限机制。

HTTP/gRPC 层本次未实现。上线前需要定义鉴权、条件写入、请求去重、超时、错误结构与版本兼容，而不是暴露一个无鉴权的万能 `/execute`。

## 生命周期与调度

一个机器人平台可有多个 Hub 实例，但它们如共享资源，应共用 journal 和统一资源命名。服务端口生命周期归应用管理；停用决策器前先停止新认知调用并等待存量操作。

内核提供一轮 propose/execute/reconcile，不会在后台无限执行。需要托管完整目标的宿主可以启用 `IntentRuntime`（见 `docs/runtime.md`）：它把预算、目标验收、结构化等待、慢思考往返和重启恢复收进 Run，但仍由宿主决定何时调用 `step()`。事件订阅、节拍和并发度始终归宿主。

## 人类慢思考

收到 deliberation 后展示：目标、stateVersion、缺少判断的原因。用户回应由你的 HMI/业务服务认证、保存并修订意图；之后重新观察和 propose。

普通文本回答不能提升权限。批准动作、提供事实和修改策略在宿主中应是不同事件。旧提案的有效期不因人工回应自动延长。

# v0.2 两个游戏的重新接入与评价

验证日期：2026-09-19。开始基线：`main@15b585c`；验证的修复代码随后出现在当前提交 `7724010`。包元数据仍为 `0.1.0`、private；本文的 v0.2 指主分支已完成的功能，不代表 npm 发布。

## 接入范围

两个游戏仍独立放在 `~/workspace/cognitive-hub-spaceship` 和 `~/workspace/cognitive-hub-danmaku`。均通过 `file:../CognitiveHub` 的公共导出接入；弹幕游戏不再安装 `da118ac` 旧快照。用户这次明确授权直接修复核心，游戏规则没有移入本仓库。

- 飞船：整段航程使用 `IntentRuntime`。插件缺失或授权不足进入 deliberating；插件重接以 fact 回应唤醒；舰长改变目标或燃料授权后修订 intent；GoalEvaluator 根据模拟器状态验收抵港/损毁。
- 弹幕：整场战斗使用 `IntentRuntime`，在 200 ms 控制完成后推进。运行时管理 operationId、未完成动作核对、预算和战斗目标验收。物理仍为 60 Hz，预测走位仍由游戏插件实现。可选 Jev 战术层是单次选择，继续使用单轮 Hub。
- 两者使用 `MemoryDecisionStore`；导出包含 Run、决策记录、执行证据与 timeline。集成测试验证 `reevaluate()` 不改变世界、不增发动作。

## 在当前核心复现并修复的三个问题

| 问题 | 修复 | 验证 |
| --- | --- | --- |
| 执行指纹是 intent/action 的规范 JSON，却用限制 512 字符的 identifier 校验；弹幕首个动作实际为 747 字符 | 改为非空字符串校验，保留原指纹内容和幂等比较 | 长动作提交、同 operation 重试、导入 journal 后核对且执行一次；Memory/Pg 共享存储合约；浏览器实际 747 字符动作通过 |
| `IntentRuntime.step()` 用完提案后没有释放，靠 TTL 被动回收，达到 maxProposals 会意外请求新判断 | 对 runtime 创建的提案统一 finally discard | 固定时钟、maxProposals=1 连续三步仍可完成，不依赖时间过期 |
| GoalEvaluator 判定 unreachable 时直接结束 Run，可能留下 accepted/pending 操作无人接续 | 与 satisfied 一样，先等在途动作核对结束，再根据现场证据结束 Run | 在途动作期间目标不可达，保持 waiting；动作完成后 failed；无 unsettled 记录且可停止插件 |

三项行为均先观察回归测试失败，再修复。未改变对 unknown 的处理；不会为了恢复而盲目重发。

## 它到底有没有帮助

飞船的帮助明确：持续目标、约束导致的阻塞、人的回应、目标修订、完成证据，本来就是这个玩法的重要部分。v0.2 给这些流程一个可查询、可追踪的 Run，应用不再自行编排 propose/execute/discard。领域的燃料预算、救援规则和界面仍需宿主实现。

弹幕的帮助较窄：有限动作的接收/核对、能力拔插边界、战斗记录和目标状态统一起来了。躲避预测、碰撞、弹幕生成、难度和即时帧调度仍由游戏负责。若目标只是做一个单机弹幕游戏，直接控制器会更简单；若目标是实验可替换的决策器并追查执行结果，Hub 有实际价值。

不能声称接入让总代码变少：弹幕控制器从 382 行到 417 行，飞船适配器从 422 行到 509 行。手写的动作接续移入库，同时增加了目标验收、Run 响应和完整决策导出。收益是少维护一套通用生命周期及获得额外能力，而不是零接入成本。

同一个修复后核心、同一自动演示，对比原手工控制器与“IntentRuntime + 决策记录”：排除一轮预热、交替顺序三轮，本机 Node 有效控制步中位耗时约 0.52–0.54 ms 与 1.13–1.16 ms；P95 约 1.35–1.56 ms 与 2.60–2.99 ms。游戏结果一致。这是本地诊断，不是浏览器 FPS、独立的 Runtime 开销测量或通用基准；新增记录也包含在成本内。

## 保留的边界与建议

1. 保持分层：物理和紧急控制在宿主，Hub 管理有限动作或较慢的任务决策。不要把网络模型放进每帧移动。
2. `busy`/帧请求合并仍由宿主负责。Runtime 的逐 Run 串行化会排队，不能自动替宿主丢弃过时的帧请求。
3. 取消仍由宿主物理引擎负责；`stop()` 只停止新派发并核对旧操作。通用 cancel 端口需真实外部执行器的需求支撑，不应为了这两个模拟游戏加入。
4. 当前 step 会读取 Run 的历史操作，完整决策记录也会增长。当前 90 秒约 450 动作已实测可用；长时间/高频运行需单独测量存储与历史读取成本。
5. 游戏仍使用内存存储。库有持久化与恢复机制，不等于游戏已经实现跨进程恢复；物理世界也需要独立保存。读回决策不等于重放整个物理世界。
6. 将真实消费端链路保留为升级门槛。核心测试通过不能代替启动游戏、导出实际记录和检查 UI。

# ADR 0003 — 托管运行时：显式 step，而不是后台循环

状态：已采用。日期：2026-09-19。

## 背景

单轮内核让宿主自己写循环、目标完成判断、慢思考往返和重启恢复。这些机制在每个产品里都会重复。v0.2 需要一层可选的运行时把它们收进来，同时不改变单轮 API，也不迫使宿主交出流程控制权。

## 决策

1. **显式 `step(runId)`，没有后台循环。** 运行时每次推进一步、至多派发一个动作，`due()` 告诉宿主谁该推进。事件订阅、节拍和并发度仍由宿主决定。理由：与 docs/integration.md 既有约定一致，可测、可停、可嵌入任何现有调度器。
2. **Run 只持久化可恢复状态。** observing/deciding/executing 是 step 的内部阶段，不进 `status`。派发真相只在执行日志；先写 operationId 再派发，崩溃后按查询恢复而不是重跑。
3. **运行时构造内部的 Hub。** 这样它能包装慢思考通道，把 `hub.propose()` 产生的请求打上 `runId` 和 `kind`。宿主仍可通过 `runtime.hub` 使用单轮 API。
4. **`Guidance` 与 `Policy` 严格分开。** 人提供的判断标准是带版本的数据，进 `DecisionRequest.guidance`；授权只来自 `Policy`。任何回应都不能放宽授权。
5. **四类回应，按请求 id 与意图修订门控。** fact 只触发重新观察；guidance 版本必须递增；approve 绑定动作 digest 与状态版本且下一步重新 propose；terminate 先 stopping 再 stopped。旧提案永远不会被直接执行。
6. **目标验收是必选宿主端口。** `GoalEvaluator` 用宿主证据判断，开始前先查一次；satisfied 但有在途操作不完成；决策器输出永远不进入它。
7. **所有权租约按 owner 身份。** 同一 owner 重启后接管自己的租约，不同 owner 需等过期。这是单工作进程的崩溃恢复，不是分布式调度。
8. **停止不等于撤销。** `stop()` 与 terminate 只停止新动作，在途操作继续核对；取消需要将来能力契约的显式 cancel 端口。

## 代价

- 每步至少两次 Run 写入（取租约、释放租约）和两次观察（运行时一次、内核 propose 一次）。接受，换取不改单轮 API。
- 一次只处理一个动作；并行分支要用多个 Run。
- 内存 RunStore 不持久，跨进程互斥只靠租约与 CAS；PostgreSQL 存储是下一步。
- 没有取消/补偿端口，没有内置节拍器。

# ADR 0007 — 单步开销与 Run 历史无关

状态：已采用。日期：2026-09-22。

## 背景

v0.2 的 `step()` 每次都对 `Run.operations` 里的全部记录读一次 journal，并把全部记录交给 `GoalEvaluator`；`#open()`（stop/terminate 用）同样遍历全部；`due()` 把所有未终态 Run 整体读出再过滤，PostgreSQL 的 `wake_at` 列与索引写了却没有查询读取；每次写入都深拷贝整个 Run。三个游戏里一局就有数百个动作，弹幕约 450 个，浇给每个角色约 63 个。在修复前的 219082c 上，用 `scripts/bench-step.mjs`（一个 Run、每步一个立即完成并验证的动作）测得：

| 存储 | 第 n 个动作 | 每步耗时 | 每步读 journal | 每步写 Run | 每步 SQL |
| --- | --- | --- | --- | --- | --- |
| 内存 | 100 / 2000 | 0.25 / 1.8 ms | 100 / 2000 | 4 | 无 |
| PGlite | 100 / 1000 | 12 / 120 ms | 100 / 1000 | 4 | 110 / 1010 |

PGlite 在进程内，没有网络往返；换成真实数据库服务器只会更差。

## 决策

1. **已终态前缀的游标 `Run.settled`。** 终态记录永不改写（内存与 PostgreSQL 的 replace 都拒绝），所以“前 k 个操作都已终态”一旦成立就永远成立。核对与 `#open()` 只看游标之后的窗口。幽灵记录与被拒绝的派发总在窗口末尾，删除它们不影响前缀。游标缺失、非整数或超出长度都读作 0，代价只是一次追平。
2. **游标在目标验收成功之后才前移。** 它和 `progress` 一起暂存，随本步最后一次写入保存。由此得到新的 `GoalEvaluator.records` 契约：此前成功验收尚未见过其终态的操作，每个操作进入终态后至少出现一次；新增 `operations`（全部 id），需要历史的验收器自己读 journal。调研时三个游戏与内核测试都没有用 `records` 的历史，所以不提供“全部历史”的开关，避免保留一条已知线性的路径。
3. **可选的 `RunStore.due(now, limit?)`。** 语义由 `runWakeAt` 定义：active/stopping 取最后更新时间，等待取最早时间界，未投递通知取重试时间，其余为 null。`PgRunStore` 用已有的部分索引查询（EXPLAIN 确认走 `cognitive_hub_runs_due`），`MemoryRunStore` 与运行时回退共用 `dueRuns` 排序：最早在前，同时刻按 id。不需要 schema 迁移：v1 起每次写入都经过同一个计算。
4. **安静检查。** 只等状态或时间、没有未终态操作、没有租约、时间界未到的 Run，`step()` 先只读观测；条件都不成立就零写入返回。条件成立时把观测交给完整路径复用。它不写存储，所以与另一进程的 `deliver()` 不会产生 CAS 冲突，最坏情况是返回一个稍旧的 `waiting`。
5. **观测复用。** `propose(intent, { observation })` 在观测仍有效时复用运行时刚取的观测，过期则自己观测。`execute()` 的重新观测与版本比对保留，派发条件不变。每个动作步的观测从 3 次降到 2 次。
6. **租约释放并入最后一次写入。** 已派发且已终态的路径保持 4 次写入：operationId 必须在派发前写入，而在派发前释放租约会让别的 worker 把尚未 claim 的 id 当成幽灵删除；决策计数的写入是反复崩溃时 `maxDecisions` 仍然有效的保证。其余路径各省一次写入；等待被唤醒的状态变化也改为暂存。
7. **只拷贝补丁。** 运行时持有的 Run 都已深度冻结，写入时只拷贝补丁，不再每次深拷贝整个快照。

## 结果

同一脚本在本提交上测得，命令为 `npm run bench`：

| 存储 | 第 n 个动作 | 每步耗时 | 每步读 journal | 每步写 Run | 每步 SQL |
| --- | --- | --- | --- | --- | --- |
| 内存 | 100 / 2000 | 0.21 / 0.86 ms | 2 | 4 | 无 |
| PGlite | 100 / 1000 | 2.2 / 5.2 ms | 2 | 4 | 10 |

接受回执的路径每步 1 次 reconcile、3 次读、4 次写；空闲等待的轮询是 0 次写、0 次读、至多 1 次观测。`tests/runtime-scale.test.mjs` 用计数而不是计时锁定这些数字：200 步里第 10 步以后每步的读、写、观测、SQL 条数完全相同。

## 代价与遗留

- **不支持降级。** 旧版本不认识 `settled`，会忽略它，但语义仍正确。旧版本的 `GoalEvaluator` 实现若依赖 `records` 的完整历史，升级后需要改为读 journal。
- **备份必须一致恢复。** journal 与 run store 从不同时间点恢复时，游标可能覆盖一条又变回未终态的记录。要么一起恢复，要么删除 `settled`。
- **字节仍随历史增长。** `operations` 与 `processedEvents` 仍是完整列表，每次写入都要序列化它们，所以 PGlite 上的耗时仍从 2.2 ms 缓慢涨到 5.2 ms，而语句条数不变。压缩或外移这两个列表需要改变 Run 的形状，留给后续版本。
- 宿主若直接改写 `operations`，必须同时删除 `settled`。

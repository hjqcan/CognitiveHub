# ADR 0009 — 多 Run 宿主的通用件与记录保留

状态：已采用。日期：2026-09-22。

## 背景

浇给每局推进 8 个 Run，并手写了四样东西：先进先出、可中止的信号量，一个跨 Run 的调用预算，按依赖顺序停插件，以及每个角色一个在途请求的保护。它的信号量写出过一个真实缺陷：配置的并发是 2，实际同时在途 4 个。飞船重置和弹幕退出也各写了一遍"停 Run、推进、按依赖顺序停插件"。

## 决策：多 Run 宿主

1. **`stepDue()` 放在运行时上。** 它只推进一遍、不循环不休眠，"调度归宿主"不变。它需要运行时的到期排序才能在截断时公平：按唤醒时间排序，刚推进过的 Run 排到后面。单个 Run 的错误记在结果里，不让整批失败，因为观测或目标验收抛错本来就会从 `step()` 抛出。
2. **`DecisionLimiter` 是一个决策器装饰器，不是运行时选项。** 同一个限流器可以被多个运行时、多个 Hub 共用。
   - 槽位在被包装的调用真正结束时才释放。调用方超时放弃的调用仍是一次真实的供应商请求，提前释放正是"并发 2 却 4 个在途"的来源。
   - 释放的槽位直接交给下一个等待者，新来者插不进去。
   - 预算在派发时计数。排队中被取消的调用不花预算，失败的调用照算。
   - 预算用完返回 `deliberate` 而不是抛错。抛错在 `onDecisionError: 'wait'` 下会一直重试到无进展上限，而预算耗尽需要宿主立即知道。
   - 不做"每个角色一个在途请求"：Hub 已经保证每个意图同一时刻只有一轮 propose。
3. **不提供通用路由器。** 三个游戏的路由都是领域逻辑：训练规则或 Jev、合成的等待、各自的预算。provider 溯源已由 `Decision.provider` 解决（ADR 0008）。
4. **`PluginHost.stopAll()`。**
   - 按 requires/provides 分轮，每轮并发停止。依次停止会让第一个慢的排空耗光共享的 signal。
   - 部分失败不抛错。排空被中止、仍在 draining 的插件继续持有它依赖的服务，这些服务记为 skipped；清理失败（failed）的插件不再持有，与 `stop()` 的依赖规则一致。

# ADR 0010 — 旁路 Run：只提案与预检，按宿主实际决定比较

状态：已采用。日期：2026-09-22。

## 背景

路线图阶段 A 要求先对一个真实宿主做只读、旁路的接入：不下发任何动作，人工评估候选召回、决策建议和拒绝行为。v0.2 的 Run 只能派发（`automatic`）或逐步请示后派发（`each-action`）。宿主若想旁听，只能自己调用单轮 `propose()` 并自己管理节奏、预算和记录。

## 决策

1. **第三种批准模式 `advisory`，而不是一个新的 Run 类型。** 旁路 Run 复用全部机制：租约、观测、目标验收、预算、决策记录、等待与唤醒、`stepDue()`。区别只在派发这一步。
2. **预检，但不派发。** 建议之后做一次 `execute(..., { live: false })`，重新观测、做 execute 阶段的策略检查、validate、调用能力无副作用的 check。预检被拒绝的码就是“宿主会拒绝”的证据，作为步进码与事件字段记录。不 claim、不占资源，所以同一资源可以同时被真正行动的 Run 使用。
3. **安静时不花预算。** 建议后等状态变化；只因时间界到期而状态没变时重新挂起，不调用决策器、不计无进展。截止时间照常生效。
4. **比较是纯函数。** `compareAdvice(records, labels)` 以宿主标注的实际决定（能力 + 候选 key，或什么都没做）对照决策记录，分别给出：
   - 一致率，衡量决策器；
   - 召回率，衡量能力适配器；
   - 不同、弃权、越权的次数，以及召回失败的决策。
   标注格式只依赖记录里已有的候选，不引入新存储。CLI 的 `--labels` 对导出的 JSON 做同样的事。

## 代价

- 标注由宿主负责。内核不知道平台实际做了什么，也不猜。
- 预检只调用 check 这类无副作用的方法，不证明执行会成功；“建议与宿主一致”也不是执行证据。
- 旁路 Run 的决策记录与行动 Run 一样增长，需要 `runtime.prune()` 或 `recordFacts: false`。

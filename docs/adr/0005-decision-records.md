# ADR 0005 — 决策记录与只读回放

状态：已采用。日期：2026-09-19。

## 背景

事件只含 ID 与状态，回答不了"为什么这次没选那个能力"。评估新模型版本、复盘一次运行、向人解释一个动作，都需要把每轮 propose 的输入输出留下来，并且能在不产生任何副作用的前提下重新审视。

## 决策

1. **记录只来自 propose 已经计算的内容。** 观测版本、未被请求的能力、每个能力的草案数、被策略排除的动作与原因、决策器看到的完整请求、决策、结果种类、错误码、提案或请求 ID。不增加模型调用，不引入新的判断。
2. **写入失败不致命。** `DecisionStore` 是观测面，不是授权也不是执行日志：append/link 失败计入 `observerErrors` 并发事件，结果不变。执行的真相仍只在 journal。
3. **存完整请求。** 没有它就无法重评；它含观测事实与候选参数，治理要求与 journal 相同。
4. **执行后回填。** 提案携带决策记录 ID，journal claim 成功后 `link(decisionId, recordId)`，决策与动作一一对应。
5. **通用 tags 而不是 runId 专用字段。** 托管运行时写 `tags.runId`；宿主可以加 trace id 等其他标签。查询按 intent 与单个标签过滤。
6. **回放不构造 Hub。** `timeline()` 只读三个存储；`reevaluate()` 只把记录的请求交给一个决策器并比较选择，绝不派发。CLI 只读导出的 JSON；`--reevaluate jev` 需要显式密钥。
7. **PostgreSQL 模式升到版本 2。** 新增决策表，jsonb 标签用 GIN 索引；迁移仍幂等，每个版本记录自己。

## 代价

- 每轮多一次存储写入，完整请求可能不小；需要 retention。
- 只记录 propose；execute 阶段的预检拒绝只在事件与拒绝码里，不进决策记录。
- 重评比较的是选择是否一致，不评估选择是否正确；正确性仍要靠真实结果与人。
